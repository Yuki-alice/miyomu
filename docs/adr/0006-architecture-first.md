# ADR-0006：架构优先的 Strangler 迁移

- 状态：Accepted
- 日期：2026-10-31

## 背景

两条路线：

- A：先换皮 UI，再改架构；
- B：先改架构，再换 UI。

Kototoro 的 `app` 有约 1,900 个主源码文件，Hilt/ViewModel/平台代码深度耦合。先换皮会把旧耦合全部继承，之后还要再改一次。

## 决策

采用 **B：架构优先 + Strangler 迁移**：

1. 新仓库，选择性复制 Kototoro 的 core/feature 代码。
2. 先抽 `core:reader`、`core:source`、`core:database`、`core:data`。
3. 新 feature 模块只依赖 core 接口，不依赖旧 `app`。
4. 旧 UI 不迁移；新 UI 用 MD3E 重写。
5. 旧 UI 仅作为行为对照，功能 parity 后删除。
6. MD3E 原型与架构迁移并行，但不阻塞迁移。

## 理由

- 避免“新 UI 继承旧架构”的返工。
- 每步可构建/可回滚，风险可控。
- 核心逻辑直接复制，UI/DI/导航新写，兼顾速度与结构。
- 设计与实现并行，缩短总周期。

## 后果

### 正面

- 模块边界清晰，UI 只依赖接口。
- 数据/源/阅读器行为保持一致。
- 旧代码可作为测试 oracle。

### 负面

- 迁移期存在两套入口/两套 UI。
- 需要维护 feature flag/对比测试。
- 复制代码需要许可证审计与包名策略。

## 约束

- 每个 feature 迁移前先定义接口与验收用例。
- 新模块禁止 Hilt 注解；Hilt 只允许在 legacy 适配层。
- 旧 UI 不得成为新 UI 的依赖。
- 每个阶段结束必须能构建、能跑关键路径。

## 备选方案

- **先换皮**：上线快，但返工大；放弃。
- **一次性重写**：风险最高；放弃。
